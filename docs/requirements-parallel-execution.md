# 並列実行最適化機能 — 概要要件定義

> Auto モードでのモデル自動選択が **並列タスク実行のボトルネック** にならないようにする仕組み。
>
> 前提：[[モデル動的選択・学習機能]] / [[完全無料・完全ローカル構成]]（VRAM 16GB）

---

## 1. 課題

### 1.1 ボトルネックの構造

| 要因 | 影響 |
|------|------|
| **VRAM 制約** | 32B モデル（14GB）は同時 1 個しか乗らない |
| **モデルロード時間** | コールド起動 10-60 秒、毎回切替するとオーバーヘッド甚大 |
| **タスクごとの最適モデル差異** | Auto モードでモデルが頻繁に切り替わる |
| **GPU 占有性** | 推論中は他タスクが GPU を使えない |

### 1.2 単純な Auto モード実装が抱える問題

```
タスクA (要 32B) → モデル切替 → 実行 → アンロード
タスクB (要 8B)  → モデルロード → 実行 → アンロード
タスクC (要 32B) → モデルロード → 実行 → アンロード
タスクD (要 14B) → モデルロード → 実行 → アンロード
```

→ **スワッピング地獄**：実行時間の半分以上がモデルロード待ち

## 2. 設計方針

### 2.1 4 つの原則

| # | 原則 | 内容 |
|---|------|------|
| P-01 | **モデル親和性** | 既にロード済みモデルで「許容できる」タスクはそれを使う |
| P-02 | **バッチ集約** | 同モデルを要求するタスクをまとめて連続実行 |
| P-03 | **VRAM 分割** | 小型モデル複数の同時起動を許可（8B + 7B = 13GB 等） |
| P-04 | **投機的プリロード** | キュー先読みで次モデルを予測ロード |

### 2.2 並列度の階層

| 層 | 並列度 | 実装 |
|---|--------|------|
| **同一モデル並列** | バッチ推論で複数リクエスト同時処理 | vLLM の continuous batching / Ollama の parallel requests |
| **複数モデル並列** | VRAM が許す範囲で別モデルを別 GPU 領域に展開 | モデルサイズ合計 ≤ 16GB |
| **CPU/GPU ハイブリッド** | 小型モデルを CPU 推論にオフロード | llama.cpp CPU mode |

## 3. 機能要件

### 3.1 GPU リソース管理

| # | 要件 |
|---|------|
| F-P01 | **GPU State Manager** が現在のロード済みモデル・VRAM 使用量をリアルタイム把握 |
| F-P02 | VRAM 残量に応じて、追加モデルロード可否を判定 |
| F-P03 | アイドル時間が閾値（例：300秒）を超えたモデルは自動アンロード |
| F-P04 | キュー内タスクから「次にロードすべきモデル」を予測し投機的にプリロード |
| F-P05 | OOM 発生時は最も古い・最も使われていないモデルを退避（LRU） |

### 3.2 タスクキュー設計

| # | 要件 |
|---|------|
| F-P06 | キューはモデルごとの **サブキュー** に分割される |
| F-P07 | スケジューラは以下の優先順位で次タスクを決定： |
|     | 1. 優先度（priority）高 |
|     | 2. ロード済みモデルを要求するタスク |
|     | 3. FIFO（同条件内） |
| F-P08 | タスク投入時に **deadline / priority** を指定可能 |
| F-P09 | 同モデルタスクの連続実行数に上限を設け、スターベーション防止（例：最大 10 件で次モデルへ譲る） |

### 3.3 モデル親和性スコア

| # | 要件 |
|---|------|
| F-P10 | モデル選択時、候補モデルごとに **総合スコア** を計算： |
|     | `score = expected_accuracy × accuracy_weight - swap_cost × latency_weight` |
| F-P11 | `swap_cost` は以下から算出： |
|     | - ロード済み = 0 |
|     | - 未ロード（VRAM 余裕あり）= ロード時間秒数 |
|     | - 未ロード（要退避）= ロード時間 + 退避モデルの再ロード期待値 |
| F-P12 | `latency_sensitivity = interactive` のタスクはロード済みを強く優先 |
| F-P13 | `latency_sensitivity = batch` のタスクは精度を強く優先 |

### 3.4 バッチ集約

| # | 要件 |
|---|------|
| F-P14 | キューを定期的にスキャンし、同モデルを要求するタスクを **連続実行クラスタ** にまとめる |
| F-P15 | クラスタサイズ上限（例：10件）でスターベーション防止 |
| F-P16 | 同モデル内では並列バッチ推論を活用（vLLM / Ollama の `num_parallel`） |

### 3.5 複数モデル同時起動

| # | 要件 |
|---|------|
| F-P17 | VRAM 使用量合計が制限内なら **複数モデルの同時ロード** を許可 |
| F-P18 | 同時起動可能な代表的組み合わせを **プロファイル** として定義： |
|     | - Profile A：32B Q3（14GB）単独 |
|     | - Profile B：14B Q4（9GB）+ 8B Q4（5GB）= 14GB |
|     | - Profile C：8B Q4 × 2（10GB）+ 埋め込み（1GB）= 11GB |
| F-P19 | スケジューラはキュー状態を見てプロファイルを動的切替 |

### 3.6 投機的プリロード

| # | 要件 |
|---|------|
| F-P20 | 現在実行中タスクの **残り時間** とキュー先頭の **次モデル要求** を見て、空き VRAM が許せば次モデルを先行ロード |
| F-P21 | プリロード対象は実行確度が高い場合のみ（過去パターンから推定） |
| F-P22 | プリロード中に高優先度タスクが来た場合は中断可能 |

### 3.7 Auto モードのデグラデーション

| # | 要件 |
|---|------|
| F-P23 | キュー深度・GPU 使用率が閾値超過時、Auto モードは **「親和性優先」** に振る舞いを切替 |
| F-P24 | 通常時は精度優先（学習済み推奨）、過負荷時はスループット優先 |
| F-P25 | 切替は閾値ヒステリシスで実装（チャタリング防止） |

### 3.8 タスク中断・優先度反映

| # | 要件 |
|---|------|
| F-P26 | 高優先度タスクが来た時、実行中の低優先度タスクを **チェックポイント保存して中断** 可能（オプション機能） |
| F-P27 | 中断発生時はログに記録し、後で再開 |
| F-P28 | リアルタイムタスク（`latency_sensitivity=interactive`）はバッチタスクを待たせない |

## 5. データモデル

### 5.1 GPU 状態

```yaml
gpu_state:
  total_vram_gb: 16
  used_vram_gb: 14
  free_vram_gb: 2
  loaded_models:
    - id: qwen2.5-32b-instruct-q3
      vram_gb: 14
      loaded_at: "2026-05-22T15:00:00Z"
      last_used_at: "2026-05-22T15:30:00Z"
      pending_tasks: 3
  active_profile: "Profile A (32B single)"
```

### 5.2 タスク拡張属性

```yaml
task:
  id: task-456
  agent_id: brand-voice
  priority: 5  # 1-10
  deadline: "2026-05-22T20:00:00Z"
  latency_sensitivity: batch
  required_accuracy: high
  candidate_models:
    - id: qwen2.5-32b-instruct-q3
      expected_accuracy: 0.85
      affinity_bonus: 0.0   # ロード済みかどうかで動的に変わる
    - id: qwen2.5-14b-q4
      expected_accuracy: 0.72
      affinity_bonus: 0.3   # こちらがロード済みなら
  selected_model: null   # スケジューリング後に決定
```

### 5.3 設定追加

```yaml
parallel:
  enable_multi_model: true
  vram_total_gb: 16
  vram_safety_margin_gb: 1   # 14GB 上限で運用

  profiles:
    - name: "single-32b"
      models: [qwen2.5-32b-instruct-q3]
    - name: "14b-plus-8b"
      models: [qwen2.5-14b-q4, llama3.1-8b-q4]
    - name: "dual-8b"
      models: [llama3.1-8b-q4, qwen2.5-7b-q4]

  scheduling:
    max_consecutive_same_model: 10
    idle_unload_seconds: 300
    speculative_preload: true

  affinity:
    accuracy_weight: 0.7
    latency_weight: 0.3
    interactive_latency_boost: 2.0  # interactive は親和性を強く重視

  degradation:
    high_load_queue_threshold: 20
    high_load_gpu_threshold_pct: 90
    hysteresis_seconds: 30
```

## 6. シナリオ

### 6.1 シナリオ A：夜間バッチ運用

```
22:00 キュー状態：
  Queue 32B Coder: 50 件（§01 QA）
  Queue 32B Inst : 30 件（§02 Content）
  Queue 14B      : 20 件（分類タスク）

→ スケジューラ判断：
  1. Profile A で 32B Coder を 10 件連続実行
  2. プリロード：32B Inst を投機的にロード（VRAM 不足なら待機）
  3. 32B Coder 完了 → アンロード → 32B Inst へ
  4. Inst 30 件連続実行
  5. 完了後 Profile B（14B + 8B）に切替し並列処理
```

### 6.2 シナリオ B：インタラクティブ混在

```
状況：
  ロード済み: 14B Q4
  キュー: [タスクX(要 32B, accuracy=high), タスクY(要 14B, interactive)]

→ Auto モード判断：
  - タスクYを先に実行（ロード済み・interactive 優先）
  - タスクY実行中に投機的に 32B プリロード（VRAM 余裕なし → 待機）
  - タスクY完了 → 14B アンロード → 32B ロード → タスクX
```

### 6.3 シナリオ C：高負荷時のデグラデーション

```
キュー深度: 50 件超
GPU 使用率: 95%

→ Auto モード：精度優先 から 親和性優先 へ自動切替
→ 推奨モデルが未ロードでも、ロード済みモデルで「許容範囲」なら採用
→ スループット 2-3 倍向上、平均精度は数% 低下（許容）
```

## 7. CLI / API

### 7.1 CLI コマンド

```bash
# 現在の GPU 状態
airflow gpu status
# => VRAM: 14/16 GB used | Loaded: qwen2.5-32b-instruct-q3 | Profile: single-32b

# スケジューラ状態
airflow scheduler status
# => Queue depth: 32B=12, 14B=5, 8B=2 | Mode: normal (accuracy-priority)

# プロファイル手動切替
airflow profile switch 14b-plus-8b

# モデル強制アンロード
airflow gpu unload qwen2.5-32b-instruct-q3

# デグラデーションモードを手動有効化
airflow scheduler degrade --on
```

### 7.2 MCP ツール公開

| ツール名 | 機能 |
|---------|------|
| `scheduler.queue_status` | 各キューの深度・待機時間 |
| `gpu.state` | VRAM 使用量・ロード済みモデル |
| `gpu.unload` | モデル明示アンロード |
| `profile.switch` | プロファイル切替 |

## 8. パフォーマンス目標

| 指標 | 目標値 |
|------|------|
| **平均モデルスワップ回数** | 単純実装比 **1/5 以下** |
| **GPU アイドル率**（タスクあり時） | **10% 以下** |
| **interactive タスクの p95 レイテンシ** | **3 秒以内** |
| **バッチタスクスループット** | 単純実装比 **2-3 倍** |
| **キュー待ち時間 p95** | キュー深度 20 で **10 分以内** |

## 9. 想定リスクと対策

| リスク | 影響 | 対策 |
|------|------|------|
| 親和性優先による精度低下 | 結果品質劣化 | 精度差が閾値以上の時のみ切替 |
| 投機的プリロードが外れる | VRAM 無駄遣い | プリロード確度の学習で精度改善 |
| 特定モデルの常駐独占 | 他タスクが進まない | `max_consecutive_same_model` 上限 |
| デグラデーション頻発 | 学習データが偏る | 通常時のデータを別途確保 |
| プロファイル切替コスト | 全モデルアンロード必要 | プロファイル間共通モデルは維持 |
| VRAM 断片化 | OOM | 定期的に全アンロード→再ロード |

|-------|------|-----|
| **P-Phase 1** | GPU State Manager + 単一モデル LRU 管理 | 1 週間 |

| **P-Phase 3** | 親和性スコア + Auto モード統合 | 2 週間 |

| **P-Phase 5** | 投機的プリロード + デグラデーション | 2 週間 |
