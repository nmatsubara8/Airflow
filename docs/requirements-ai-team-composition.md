# AI チーム構成 — 詳細要件定義

> Rio の AI チーム構成（調整層 + §01 エンジニアリング + §02 コンテンツ + §03 ビジネス）を、エージェント単位の責任範囲・入出力・トリガー・エスカレーション基準まで詳細化したもの。

## プラットフォーム確認事項

| プラットフォーム | 正式名称 | 提供元 | 用途 |
|---------------|---------|--------|------|
| **Claude Code** | Claude Code | Anthropic | 開発者向け。ターミナル・コードベース操作。§01 Engineering に使用 |
| **Cowork** | **Claude Cowork** | Anthropic | 非エンジニア向けデスクトップエージェント。ローカルファイル・アプリ横断の知識労働を自律実行。§02 Content / §03 Business に使用 |

### Claude Cowork の特徴（要件定義への影響）
- **動作環境**：Claude Desktop アプリ（macOS。Windows は計画中）。Max プラン以上で利用可能
- **操作対象**：ローカルフォルダ・ファイル・デスクトップアプリ（非ターミナル）
- **動作モデル**：「目標を渡せば残りは自律実行」— プロンプト応答型ではなくアウトカム駆動
- **Claude Code との違い**：Claude Code はコード生成・実行（開発者向け）、Claude Cowork はドキュメント整理・データ抽出・ワークフロー自動化（知識労働者向け）
- **人間監視**：重大な意思決定はユーザー確認を維持（Anthropic の安全設計）

| レイヤー | 実装プラットフォーム | 主な責務 |
|---------|------------------|---------|

| §02 Content | Claude Cowork（デスクトップエージェント） | 原稿生成・4 段レビュー |
| §03 Business | Claude Cowork（デスクトップエージェント） | 戦略ブリーフ・案件管理・契約レビュー |

## 1. 調整層 (Orchestration Layer)

### 1.1 役割

全 AI 社員が同じ場所を読み書きする **共有記憶 + タスク管理の場所**。
個別エージェントの「机」を超えて、横断的に情報を流通させる唯一のレイヤー。

### 1.2 構成要素

| コンポーネント | 種別 | 責務 |
|--------------|------|------|
| 共有タスクボード | データストア | タスク・コメント・状態の保持 |
| タスクディスパッチ | エージェント | Inbox からのタスク生成・割り振り |
| Hermes Agent | エージェント | 重複・ゴミタスクの清掃 |
| MCP サーバー群 | 通信レイヤー | 各 AI ツール（Claude Code / Cowork）の接続点 |

### 1.3 タスクディスパッチ — 詳細要件

| 項目 | 内容 |
|------|------|
| 入力 | Obsidian Inbox、GitHub Issues、メール等のノート |
| 出力 | 構造化タスク（owner・status・tags・priority） |
| トリガー | Inbox 追加検知（ポーリング or webhook） |
| 担当割り振りロジック | タグ/キーワードベース → エージェント定義の `skills.md` と照合 |
| 失敗時挙動 | 担当が決まらない場合 `needs-human` で人間に判断要求 |
| エスカレーション基準 | 同一タスクが 3 回以上ディスパッチ失敗した場合は人間に通知 |

### 1.4 Hermes Agent — 詳細要件

| 項目 | 内容 |
|------|------|
| 入力 | タスクボード全体 |
| 出力 | 重複タスクのマージ・ゴミタスクの削除ログ |
| トリガー | スケジュール実行（例：毎日 03:00） |
| 判定基準 | タイトル類似度（しきい値 0.85 以上）+ owner/status 一致 |
| 制約 | 過去 24 時間以内に更新されたタスクは削除対象外 |
| エスカレーション基準 | 削除候補が 1 日 50 件を超えた場合は人間に確認 |

## 2. §01 Engineering（Claude Code）

### 2.1 セクション概要

エンジニアリング業務（実装・QA・セキュリティ・DevOps・ドキュメント）を担う。
**自律実行：夜間 QA（毎晩）** が標準スケジュール。

### 2.2 エージェント詳細

#### 2.2.1 `tech-lead`
| 項目 | 内容 |
|------|------|
| 責任範囲 | 技術方針決定・PR の最終承認判断・アーキテクチャ整合性確認 |
| 入力 | PR、設計提案タスク |
| 出力 | 承認 / 差し戻しコメント、技術判断ログ |
| エスカレーション基準 | 既存アーキテクチャを大きく変更する設計提案 → `needs-human` |

#### 2.2.2 `eng-director`
| 項目 | 内容 |
|------|------|
| 責任範囲 | スプリント進行管理・タスク優先度の整理 |
| 入力 | タスクボード全体 |
| 出力 | 週次ステータスサマリ・優先度更新 |
| トリガー | 毎週月曜 09:00 |
| エスカレーション基準 | 期日超過タスクが 30% を超えた場合 |

#### 2.2.3 `qa`
| 項目 | 内容 |
|------|------|
| 責任範囲 | 単体・統合テスト実行、テストカバレッジレポート |
| 入力 | PR、夜間バッチタスク |
| 出力 | テスト結果レポート、失敗ケース一覧 |
| トリガー | PR 作成時 + 毎晩 02:00 夜間バッチ |
| エスカレーション基準 | テスト失敗が修正不能と判断された場合 |

#### 2.2.4 `frontend`
| 項目 | 内容 |
|------|------|
| 責任範囲 | UI コンポーネント実装・スタイリング |
| 入力 | デザイン仕様・タスク |
| 出力 | コード差分、PR |
| エスカレーション基準 | デザイン仕様が不明確・矛盾している場合 |

#### 2.2.5 `backend`
| 項目 | 内容 |
|------|------|
| 責任範囲 | API・DB ロジック実装 |
| 入力 | API 仕様・タスク |
| 出力 | コード差分、PR |
| エスカレーション基準 | DB スキーマ変更が必要な場合 → `architect` へ依頼 |

#### 2.2.6 `security`
| 項目 | 内容 |
|------|------|
| 責任範囲 | 依存関係スキャン・コードの脆弱性検出・認証設定レビュー |
| 入力 | コードベース全体、PR |
| 出力 | 脆弱性レポート、修正提案 |
| トリガー | PR 作成時 + 毎晩 02:30 |
| エスカレーション基準 | Critical 脆弱性検出時は即座に人間通知 |

#### 2.2.7 `devops`
| 項目 | 内容 |
|------|------|
| 責任範囲 | CI/CD パイプライン・インフラ設定 |
| 入力 | infra-as-code 変更タスク |
| 出力 | パイプライン更新・デプロイログ |
| 制約 | **本番インフラ変更は人間承認必須** |
| エスカレーション基準 | 本番影響のある設定変更すべて |

#### 2.2.8 `architect`
| 項目 | 内容 |
|------|------|
| 責任範囲 | データモデル設計・システム設計 |
| 入力 | 設計依頼タスク |
| 出力 | 設計ドキュメント・ER 図・シーケンス図 |
| エスカレーション基準 | 既存ドメインモデルとの不整合発生時 |

#### 2.2.9 `mobile`
| 項目 | 内容 |
|------|------|
| 責任範囲 | iOS / Android 実装 |
| 入力 | モバイル向けタスク |
| 出力 | コード差分、PR |

#### 2.2.10 `data`
| 項目 | 内容 |
|------|------|
| 責任範囲 | データパイプライン・ETL・分析クエリ |
| 入力 | データ加工タスク |
| 出力 | スクリプト・データセット |

#### 2.2.11 `reviewer`
| 項目 | 内容 |
|------|------|
| 責任範囲 | PR レビュー（可読性・命名・パターン適合性） |
| 入力 | PR |
| 出力 | レビューコメント |
| エスカレーション基準 | アーキテクチャ判断が必要な場合 → `tech-lead` |

#### 2.2.12 `tester`
| 項目 | 内容 |
|------|------|
| 責任範囲 | E2E テスト・シナリオテスト作成と実行 |
| 入力 | 仕様書、新機能 PR |
| 出力 | テストスクリプト、実行ログ |

#### 2.2.13 `debugger`
| 項目 | 内容 |
|------|------|
| 責任範囲 | バグ調査・スタックトレース解析 |
| 入力 | バグレポートタスク、CI 失敗ログ |
| 出力 | 原因分析レポート、修正提案 |

#### 2.2.14 `docs`
| 項目 | 内容 |
|------|------|
| 責任範囲 | README・API ドキュメント・運用手順書の生成と更新 |
| 入力 | コード変更 PR |
| 出力 | ドキュメント差分 |
| トリガー | PR マージ後 |

### 2.3 §01 内部の連携フロー（例：新機能実装）

```
タスクディスパッチ
   ↓ (frontend タスク + backend タスク 並列割当)
frontend / backend 実装
   ↓ PR 作成
qa (自動テスト) + security (脆弱性スキャン) + reviewer (コードレビュー)
   ↓ すべて pass
tech-lead 承認 / needs-human
   ↓ マージ
docs (ドキュメント更新)
```

## 3. §02 Content（Cowork）

### 3.1 セクション概要

原稿生成のオーケストレーションと **4 段レビュー** による品質保証。

### 3.2 エージェント詳細

#### 3.2.1 `content-director`
| 項目 | 内容 |
|------|------|
| 責任範囲 | オーケストレーター。人間が書いた台本を膨らませる |
| 入力 | 人間の台本ドラフト |
| 出力 | 膨らませた原稿、後続 3 エージェントへの引き継ぎ |
| エスカレーション基準 | 台本の意図が読み取れない場合 |

#### 3.2.2 `brand-voice`（編集者）
| 項目 | 内容 |
|------|------|
| 責任範囲 | ブランドボイス（価値観・喋り方）一致チェック |
| 入力 | `content-director` の出力原稿 |
| 出力 | 修正提案、合否判定 |
| 判定基準 | ブランドガイドライン（別ファイル管理）との照合 |

#### 3.2.3 `root-cause`
| 項目 | 内容 |
|------|------|
| 責任範囲 | 本質的な問題にタックルできているか・賞味期限の長い情報か |
| 入力 | `brand-voice` 通過原稿 |
| 出力 | 「表層的」「本質的」の判定 + 改善案 |
| エスカレーション基準 | 本質性が低いと判定 → `content-director` に差し戻し |

#### 3.2.4 `anti-ai-slop`
| 項目 | 内容 |
|------|------|
| 責任範囲 | AI 特有のクセ・装飾・ふざけた書き方を除去 |
| 入力 | `root-cause` 通過原稿 |
| 出力 | クリーンアップ済み最終原稿 |
| 判定基準 | 過剰な絵文字・ハイフン区切り・冗長な前置きの検出 |

#### 3.2.5 `morning-brainstorm`
| 項目 | 内容 |
|------|------|
| 責任範囲 | 朝のブレインストーミング・新規企画ネタの自動生成 |
| 入力 | 過去原稿・トレンドデータ |
| 出力 | 企画候補リスト |
| トリガー | 毎朝 07:00 |

### 3.3 §02 の 4 段レビューフロー

```
人間の台本
   ↓
content-director (膨らませ)
   ↓
brand-voice (ブランド一致チェック)        ─┐
   ↓                                     │
root-cause (本質性チェック)               ├ 4 段レビュー
   ↓                                     │
anti-ai-slop (AI 臭除去)                  ─┘
   ↓
完成原稿
```

## 4. §03 Business（Cowork）

### 4.1 セクション概要

ビジネス側（マーケ・戦略・案件管理・契約レビュー）の自動化。

### 4.2 エージェント詳細

#### 4.2.1 `marketing-director`
| 項目 | 内容 |
|------|------|
| 責任範囲 | デザインコンサル宣伝・マーケ施策のブリーフ |
| 入力 | KPI ダッシュボード・過去施策ログ |
| 出力 | 施策ブリーフ（数日おき） |
| トリガー | 週 2 回（火・金 09:00） |

#### 4.2.2 `business-strategy`
| 項目 | 内容 |
|------|------|
| 責任範囲 | ビジネス戦略立案・市場分析 |
| 入力 | 市場データ・社内 KPI |
| 出力 | 戦略ブリーフ |
| トリガー | 週次 |
| エスカレーション基準 | 大きな方向転換提案は人間レビュー必須 |

#### 4.2.3 `partnership-manage`
| 項目 | 内容 |
|------|------|
| 責任範囲 | 紹介すべき AI 製品のフィルタリング |
| 入力 | 案件依頼リスト |
| 出力 | 推奨可否判定 + 理由 |
| 判定基準 | **ハイプだけの製品はお断り**、本当にユニークで役立つ製品のみ推奨 |
| エスカレーション基準 | 判定が grey zone の場合 → 人間判断 |

#### 4.2.4 `legal-review`
| 項目 | 内容 |
|------|------|
| 責任範囲 | 契約書の一次レビュー |
| 入力 | 契約書ドラフト |
| 出力 | 可視性・不自然な箇所の指摘リスト |
| 制約 | **最終確認は弁護士（人間）必須** |
| エスカレーション基準 | すべての契約書 — AI は一次フィルターのみ |

## 5. クロスセクションのエスカレーションルール

| ケース | 対応 |
|-------|------|
| AI がスコープ外判断を求められた | `needs-human` に切替、理由必須 |
| Critical 脆弱性検出 | `security` → 人間に即時通知 |
| 本番インフラ変更 | `devops` → 人間承認必須 |
| 法的判断 | `legal-review` → 弁護士必須 |
| 戦略の大幅変更 | `business-strategy` → 人間レビュー必須 |
| アーキテクチャ大変更 | `tech-lead` / `architect` → 人間判断 |

## 6. エージェント定義テンプレート

各エージェントは以下の形式で `agents/<agent-name>/skills.md` に定義する：

```yaml
---
agent_id: <unique-id>
section: §01 | §02 | §03 | orchestration
platform: claude-code | claude-cowork
model: claude-sonnet-4-6 | claude-opus-4-7 | claude-haiku-4-5
context_isolation: subagent | separate-session
---

# Role
<役割の 1 行説明>

# Responsibilities
- <責務 1>
- <責務 2>

# Inputs
- <受け取るタスク種別>

# Outputs
- <生成する成果物>

# Triggers
- <起動タイミング: PR 作成時 / 毎晩 02:00 など>

# Escalation Criteria
- <`needs-human` に切り替える条件>

# Dependencies
- <連携する他エージェント>

# Tools / MCP
- <利用可能なツール一覧>
```

## 7. 実装優先度

| Phase | 範囲 | 目的 |
|-------|------|------|
| Phase 1 | 調整層（タスクボード + ディスパッチ + Hermes） | 全体の土台を作る |
| Phase 2 | §01 最小セット（`qa`, `reviewer`, `docs`, `security`） | 夜間 QA の即時価値 |
| Phase 3 | §01 拡張（`frontend`, `backend`, `tech-lead` 等） | 実装業務の自動化 |
| Phase 4 | §02 / §03（コンテンツ・ビジネス） | エンジニアリング外の自動化 |
