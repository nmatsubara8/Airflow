# 完全無料・完全ローカル構成 — 概要要件定義

> Airflow の AI チームを **VRAM 16GB の単一GPU + 量子化LLM + OSS のみ** で動かす構成。
> クラウド API・有料サブスクリプションへの依存をゼロにする。

---

## 1. 構成方針

### 1.1 制約条件

| 項目 | 制約 |
|------|------|
| GPU VRAM | **16GB**（RTX 4060 Ti 16GB / RTX 4080 / RX 7800 XT 等） |
| OS | Linux / macOS / WSL2（Windows ネイティブは beta） |
| 月額コスト | **$0**（電気代・自前ハードウェア除く） |
| 外部 API 依存 | **なし**（オフラインで動作） |
| 精度許容範囲 | 多少の失敗率を許容（人間レビューでカバー） |
| 実行時間 | バッチ・夜間処理が中心。リアルタイム性は妥協 |

### 1.2 全体スタック

```
┌────────────────────────────────────────────────────┐
│ アプリ層                                            │
│   §01 Engineering / §02 Content / §03 Business      │
│            ↓                                        │
│ エージェント実行基盤： Hermes Agent (OSS)            │
│            ↓                                        │
│ ローカル推論：         Ollama / llama.cpp           │
│            ↓                                        │
│ モデル：               量子化済み 14B〜32B          │
│            ↓                                        │
│ ハードウェア：         VRAM 16GB GPU                │
└────────────────────────────────────────────────────┘
```

## 2. 推奨モデル構成（VRAM 16GB）

### 2.1 役割別モデル振り分け

| 役割 | 推奨モデル | 量子化 | VRAM 使用 | 理由 |
|------|----------|-------|----------|------|
| **コード生成** | Qwen 2.5 Coder 32B | Q3_K_M | ~14GB | コード特化、32B クラスでも収まる |
| **文章生成・レビュー** | Qwen 2.5 32B Instruct | Q3_K_M | ~14GB | 多言語（日本語◎）、汎用性能高 |
| **構造化抽出・分類** | Qwen 2.5 14B Instruct | Q4_K_M | ~9GB | 軽量で高速、ツール呼び出し安定 |
| **要約・前処理** | Llama 3.1 8B Instruct | Q4_K_M | ~5GB | 同時起動向け軽量モデル |
| **ベクトル埋め込み** | bge-m3 / mxbai-embed-large | FP16 | ~1GB | RAG 用 |

### 2.2 単一モデル運用 vs 複数モデル切り替え

| 方針 | 説明 | 推奨ケース |
|------|------|----------|
| **単一モデル常駐** | Qwen 2.5 32B Q3_K_M を常に起動 | 切替コストを避けたい / VRAM 余裕なし |
| **モデルホットスワップ** | Ollama がタスクごとにロード | 多様なタスク・夜間バッチ |

> Ollama は VRAM を超えると CPU オフロードで動くが、速度は 5〜10 倍遅くなる。**VRAM 内に収まる量子化レベルを選ぶことが最優先**。

## 3. 精度トレードオフへの対策

### 3.1 想定される精度低下

| 比較対象 | ツール選択失敗率 | 備考 |
|---------|--------------|------|
| GPT-4o（クラウド） | 4% | 参照値 |
| Llama 3.1 70B（VRAM 40GB+） | 31% | OSS の天井 |
| **Qwen 2.5 32B Q3（VRAM 14GB）** | **〜40-50%（推定）** | 本構成の想定 |
| 14B Q4 | 50%+ | 単独運用は非推奨 |

### 3.2 精度補完メカニズム（必須実装）

| 機構 | 実装 | 目的 |
|------|------|------|
| **構造化出力の強制** | JSON Schema / Pydantic で出力フォーマット制約 | パースエラー削減 |
| **リトライ機構** | 失敗時に最大3回まで自動再実行 | 一時的なミス回収 |
| **二重実行 + 一致確認** | 重要タスクは2回実行し結果差異をチェック | 信頼性向上 |
| **エスカレーション閾値の引き下げ** | 信頼度スコア低い場合は即 `needs-human` | 人間レビューを増やす |
| **タスク分割の徹底** | 1タスク = 1判断に細分化 | 1回あたりの判断負荷を下げる |
| **Few-shot プロンプト** | 各エージェントの `skills.md` に例を3-5件含める | 精度を稼ぐ |
| **CoT（Chain of Thought）** | 推論プロセスを明示的に出力させる | ハルシネーション削減 |

### 3.3 タスク種別ごとの実行戦略

| タスク種別 | 戦略 |
|----------|------|
| 高精度必須（契約レビュー・セキュリティ判定） | **二重実行 + 人間最終確認必須** |
| 中精度許容（ドキュメント生成・要約） | 単発実行 + 人間レビュー |
| 低精度許容（タスク分類・タグ付け） | 単発実行のみ |

## 4. プラットフォーム選択

### 4.1 各セクションのツール

| セクション | ツール | 備考 |

| Hermes Agent（インフラ清掃役割） | **Cleaner Agent** | OSS の Hermes Agent と区別 |
| Hermes Agent（OSS ツール） | そのまま | 公式名称 |

## 5. システム要件

### 5.1 ハードウェア最低要件

| コンポーネント | 最低 | 推奨 |
|--------------|------|------|
| GPU VRAM | 16GB | 24GB（Q4 で 32B 動作可） |
| RAM | 32GB | 64GB |
| ストレージ | 100GB SSD | 500GB NVMe |
| CPU | 8コア | 16コア |
| ネットワーク | — | ローカル LAN のみで可 |

### 5.2 ソフトウェアスタック

| 層 | 採用ソフトウェア |
|---|----------------|
| OS | Ubuntu 22.04 LTS / macOS 14+ |
| 推論エンジン | **Ollama**（メイン）/ llama.cpp（低レベル制御用） |
| エージェントランタイム | **Hermes Agent**（Nous Research） |
| タスクボード | Git リポジトリ + JSON / Markdown ファイル |
| MCP サーバー | Ollama MCP / File-system MCP / Git MCP |
| ベクトル DB | Qdrant（ローカル）/ Chroma |
| スケジューラ | Hermes 内蔵 cron / systemd timer |

## 6. 運用パターン

### 6.1 夜間バッチ運用（推奨）

```
22:00  全エージェント起動
22:30  §01 QA：テスト実行（Qwen Coder 32B）
00:00  §02 Content：原稿レビュー4段（Qwen 32B）
02:00  §03 Business：ブリーフ生成（Qwen 32B）
03:00  Cleaner Agent：タスクボード清掃
06:00  全結果を朝のレビュー用にまとめる
07:00  人間チェック開始
```

**利点**：1台のGPUでも順次実行で時間を稼げる / 電気代も夜間電力で安価

### 6.2 日中インタラクティブ運用

| 制約 | 対応 |
|------|------|
| 32Bモデルは推論が遅い（10-30 tokens/sec） | 14B モデルに切り替え |
| 同時並列はVRAM的に不可 | キュー方式で順次実行 |

## 7. 実装フェーズ

| Phase | 内容 | 目標期間 |
|-------|------|--------|
| **Phase 0** | Ollama + Hermes Agent インストール、モデルDL、疎通確認 | 1日 |
| **Phase 1** | タスクボード（Git + JSON）構築、Cleaner Agent 実装 | 1週間 |
| **Phase 2** | §01 最小セット（QA・reviewer・docs）を Hermes + Qwen Coder で実装 | 2週間 |
| **Phase 3** | §02 Content の4段レビュー実装 + 精度補完機構の追加 | 3週間 |
| **Phase 4** | §03 Business 実装、夜間バッチスケジュール整備 | 2週間 |

## 8. 想定リスクと対策

| リスク | 影響 | 対策 |
|------|------|------|
| 量子化による精度低下 | 誤判断・誤生成 | 二重実行・人間レビュー閾値の引き下げ |
| VRAM 枯渇 | OOM クラッシュ | モデルサイズ厳守、CPU オフロード許容 |
| 推論時間長期化 | リアルタイム性低下 | 夜間バッチ運用に振る |
| OSS モデルのライセンス | 商用利用制約 | Apache 2.0 / MIT モデル優先（Qwen 2.5 は Apache 2.0） |
| 日本語精度 | §02 Content で品質低下 | Qwen 2.5（中華系・日本語強い）を採用 |
| ハードウェア初期投資 | 導入コスト | 中古 RTX 3090（24GB）等を検討 |
